# Technical concepts through the Northstar Health lab

This reference connects the reported Leaver implementation to practical IAM engineering distinctions. It does not expand the [four tests](../labs/leaver/test-scenarios.md) into untested capabilities. [Source/evidence provenance](evidence/leaver-2026-11-26.md).

| Distinction / concept | Northstar example and engineering implication |
|---|---|
| Identity Cube versus application account | Sarah's Cube brings person attributes, roles and accounts together. `Sarah_Miller` is one Oracle database account. Locking it does not delete her workforce Identity or automatically disable every other account. |
| Identity versus Link | The `Identity` object represents the person; an Oracle `Link` stores the correlated account's native identity and attributes. `iden.getLinks()` can include both HR and Oracle accounts. A Link is neither the target user nor a guarantee of fresh grants. |
| Native identity versus IIQ Identity name | Oracle requests use `link.getNativeIdentity()`, such as `Alex_Jones`. Internal `IIQ` assigned-role requests use `iden.getName()`. Employee ID, object ID, display name and account key must not be substituted for one another. |
| Business Role versus IT Role | Sarah's `dba - Business` represents the business assignment; required `dba - IT` describes technical Oracle access. The tested relationship revoked five grants on deassignment; other configurations and shared assignments may retain access. |
| SailPoint roles versus Oracle roles | An IIQ role is a `Bundle`, a governance/access-model object. `AQ_USER_ROLE` is an Oracle database role exposed as an entitlement through Oracle Application. Removing a person's Bundle assignment is different from dropping an Oracle role. |
| Assigned versus detected roles | `getAssignedRoles()` discovers explicit assignments in this lab; detected IT Role display reflects recognized technical access. Sarah's IT Role stopped displaying after access removal/reconciliation. Detection alone is not approval evidence. |
| Role-based versus direct entitlement provisioning | Sarah received access represented by a Business/IT Role hierarchy. John had direct Oracle `DBA`, `RESOURCE`, `ANALYST`, `CONNECT` grants without a Business Role. Separate cleanup stages address these two paths. |
| Direct access versus effective access | John's `DBA_ROLE_PRIVS` and `DBA_SYS_PRIVS` results describe direct grants. Effective access can involve role hierarchies, PUBLIC, object privileges and session context. Zero direct rows do not prove all access paths were tested or removed. |
| Account Aggregation versus Identity Refresh | Northstar Account Aggregation reads the authoritative CSV and correlates accounts. Identity Refresh with Process Events evaluates configured lifecycle events and other selected identity processing. After Oracle changes, Oracle aggregation and refresh reconcile the stored view; options can also cause further provisioning. |
| Provisioning versus reconciliation | LCM sends requested changes; separate aggregation/refresh reconciles IIQ's representation. Sarah's target grants were gone while her stored Link still showed them. `getObject()` returned current connector information but did not itself persist reconciliation. |
| Authoritative versus connected target application | Northstar Workday HR owns synthetic employment facts; Oracle Application enforces database account/access changes. A simulated CSV name does not establish a real Workday integration. MySQL is IIQ's persistence layer here, separate from the older JDBC source exercise. |
| Workflow variables versus result variables | `identityName` is event input; `disablePlan` holds a constructed plan. A step's `resultVariable="disablePlan"` maps its return into that workflow variable. `wfcontext.setVariable()` explicitly writes the two snapshot variables. An LCM subprocess's internal results are not automatically validated by the parent merely because a plan variable exists. |
| Conditional workflow transitions | No Oracle Link skips disabling but still reaches Business Role removal. Empty role plans skip their LCM call and reach live discovery. Empty entitlement plans skip their LCM call and stop. The graph is not twelve always-executed sequential actions. |
| XML configuration versus BeanShell execution | XML declares workflow type, variables, sibling Steps, arguments, references and transitions. BeanShell retrieves objects, evaluates conditions and builds plans. A well-formed XML file can still contain an invalid API call or incorrect runtime logic. |
| XML escaping and CDATA | A serialized Source condition uses `&amp;&amp;` so parsing returns BeanShell `&&`. CDATA is another way to hold script text; it does not fix Step nesting and cannot contain its own closing `]]>` sequence. |
| Correct step nesting | Each of the twelve Steps is a direct child of Workflow; a Step's Script and Transitions belong inside that Step. Accidentally nesting a Step inside another may remain well-formed XML while violating workflow structure. |
| Least privilege | Offboarding removes access no longer justified by employment. Broad Oracle DBA-style roles are isolated synthetic test inputs, not recommended workforce birthright access. Least-privilege connector permissions and comprehensive policy are not established by these tests. |
| Employee offboarding and access revocation | Alex proves reported locking; Sarah demonstrates one role-based removal configuration; John demonstrates direct role/system-privilege cleanup. Deletion, IIQ inactive mapping, IIQ login access and existing session termination remain distinct future controls. |
| Stored Link versus live ResourceObject | A Link can show pre-revocation values. `ConnectorFactory` obtains the configured connector; `getObject("account", ...)` retrieves a ResourceObject used by the remaining-access builder. It is a fresh decision input within connector limits, not a transaction lock or an independent database verification. |

## Plan composition in practice

The hierarchy is **ProvisioningPlan → AccountRequest → AttributeRequest**. `plan.setIdentity()` establishes the person; `plan.add()` holds a per-application account operation; `acctReq.add()` holds each attribute operation. Disable is an account operation; Remove is an attribute operation used inside Modify requests for `assignedRoles`, `ROLES` and `SYSTEM_PRIVILEGES`. Neither construction nor serialization submits the plan.
